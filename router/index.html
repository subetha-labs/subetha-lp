An API can be perfectly good and still be unreachable — not because of the data, but because it settles on a rail your wallet does not hold. SubEtha Router accepts a payment on one rail and pays the provider on another. Two legs, two separate funds. No swap, no bridge.

The barrier is the rail, not the data

Paid APIs are starting to price per call over HTTP 402. That part is converging. What has not converged is how you pay: x402 exact on one chain, MPP tempo charge on another, each with its own asset. Hold the wrong one and a perfectly documented endpoint is simply closed to you.

Without a router

You need the exact asset, on the exact chain, that each provider demands. Two providers, two rails, two funded wallets — before you read a single byte.

With the router

You pay once, on the rail you already hold. The router pays the provider on theirs, from its own funds, and returns the provider's response unchanged.

Two providers are live. Check them yourself.

These are self-hosted market-data providers we run. You do not need a wallet, an account, or our permission to see the payment contract — an unauthenticated request returns the 402 challenge, which is the whole offer in the open.

Paying for real

A paid call needs testnet funds on the matching rail — Base Sepolia USDC for the x402 provider, Tempo pathUSD for the MPP one. Both providers have settled real testnet payments end to end. The agent-facing path for doing that through the router is still being built; see Status.

Two payments, deliberately unlinked

The router does not convert anything. It takes a payment on the inbound rail and makes a separate payment on the outbound rail, each prefunded on its own chain. Calling it a swap or a bridge would be wrong.

you  →  pay on the rail you hold  →  SubEtha Router  →  pays the provider on theirs  →  provider's response, unchanged

Quote first

The router reads the provider's live offer before quoting you, so the price you approve is bound to the offer that will actually be paid.

Approve explicitly

Nothing moves on a conversational turn alone. Approval is bound to a specific quote, and an offer that changes after approval is refused.

At most once

A durable journal records each purchase. Repeat or concurrent requests do not re-send either leg, and an uncertain outcome stays uncertain rather than retrying blindly.

Why we ended up building this

We were building SubEtha — private machine payments for x402, settled on zERC20 — and kept running into the same wall from the other side: a payment method is only as useful as the set of APIs that accept it. Routing is what makes a rail worth holding. The privacy work and this are the same problem approached from two ends.

決済はテストネット。市場データはメインネットの読み取り専用参照値です。

障壁はデータではなく、レール

有料 API は HTTP 402 で 1 回ごとに課金する形に収束しつつあります。収束していないのは支払い方法です。あるチェーンでは x402 exact、別のチェーンでは MPP tempo charge、資産もそれぞれ違う。手持ちが違えば、どれだけ整備された API でも到達できません。

Router がない場合

プロバイダごとに、要求されるチェーンの、要求される資産が要ります。プロバイダが 2 つなら、レールも 2 つ、資金を入れたウォレットも 2 つ。データを 1 バイト読む前の話です。

Router がある場合

手持ちのレールで 1 回支払うだけ。Router が自分の資金でプロバイダ側のレールに支払い、プロバイダの応答をそのまま返します。

2 つのプロバイダが公開中です。ご自身で確認できます。

いずれも当方が自前でホストしているマーケットデータ提供元です。ウォレットもアカウントも許可も不要——認証なしのリクエストを送れば 402 チャレンジが返り、支払い条件がそのまま公開されています。

実際に支払う場合

有料リクエストには、該当レールのテストネット資金が要ります（x402 側は Base Sepolia の USDC、MPP 側は Tempo の pathUSD）。両プロバイダとも実テストネット決済を端から端まで通しています。Router を経由してエージェントから支払う経路は構築中です。現在地をご覧ください。

2 つの支払いは、意図的に切り離されています

Router は資産を変換しません。受信レールで支払いを受け取り、送信レールで別の支払いを行います。各レールはそれぞれのチェーンで事前に資金供給されており、交換やブリッジと説明するのは誤りです。

利用者  →  手持ちのレールで支払う  →  SubEtha Router  →  プロバイダ側のレールで支払う  →  プロバイダの応答をそのまま返す

先に見積もる

Router はプロバイダの実提示を読んでから見積もりを出すため、承認する金額は実際に支払われる提示に束縛されます。

明示的に承認する

会話のやり取りだけでは何も動きません。承認は特定の見積もりに束縛され、承認後に提示が変われば実行を拒否します。

多くとも 1 回

各購入は耐久的な journal に記録されます。再送・並行要求でもどちらのレグも再実行されず、結果が不確かな場合は不確かなまま保持し、当てずっぽうの再試行をしません。

なぜこれを作ることになったか

私たちは SubEtha——x402 の秘匿マシン決済を zERC20 で精算する仕組み——を作っていて、反対側から同じ壁に何度もぶつかりました。決済手段の有用性は、それを受け付ける API の数で決まります。ルーティングは、そのレールを持つ価値を成立させる部分です。秘匿性の取り組みとこれは、同じ問題を両端から見たものです。
